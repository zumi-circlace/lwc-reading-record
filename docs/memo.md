# 📚 読書記録アプリ（Salesforce） 開発・設計メモ

## 1. アプリ機能要件

読了した本を記録し、ダッシュボードで可視化するモバイル対応アプリ。

### 登録UI（LWCで実装）

LWCの `lightning-tabset` などを用いて、以下の3パターンで登録画面を切り替えられるようにする。

1. **カメラ読み取り:** モバイルネイティブの `lightning/barcodeScanner` を使用し、バーコードからISBNを取得 → Apex経由で外部API検索 → 登録。
2. **ISBN手打ち検索:** ISBNをテキスト入力し「検索」ボタン → Apex経由で外部API検索 → 登録。（PCからの利用や、カメラが使えない時用）
3. **完全手打ち:** APIでヒットしない同人誌や古い本などのために、「タイトル、カテゴリ、説明」を手動入力して保存するフォーム。

### データモデル（カスタムオブジェクト：`ReadingLog__c`）

* `Title__c` (テキスト): 本のタイトル
* `ISBN__c` (テキスト): ISBN（重複チェックや表紙画像取得用）
* `ReadDate__c` (日付): 読了日（デフォルトは今日）
* `Category__c` (選択リスト): 小説、ビジネス、技術書、など
* `Description__c` (ロングテキストエリア): 感想やメモ

## 2. 🛡️「俺、権限まわり分かってます」アピール設計

Salesforceエンジニアとしての価値を最も高める「セキュリティとアクセス制御」の実装方針。

### ① 組織の共有設定 (OWD) は「非公開」

* `ReadingLog__c` の組織の共有設定を **「非公開 (Private)」** に設定。
* これにより、ルール上「レコードの所有者（作成者）しか、自分の記録を閲覧・編集できない」という前提が担保される。

### ② Apexは必ず `with sharing` を付ける

* コントローラークラスの宣言を `public with sharing class BookScannerController` とする。
* これにより、OWDの「非公開」ルールがApex実行時にも強制され、他人のデータを不正に取得したり上書きしたりする脆弱性を防げる。（※実務で必須の作法）

### ③ SOQLに `WITH USER_MODE` を付ける（最新のトレンド）

* データ取得・操作時に「実行ユーザーに本当にその項目へのアクセス権（FLS）があるか」を担保する記述。（例：`SELECT Id, Title__c FROM ReadingLog__c WITH USER_MODE`）。これをやっておくと「最新のセキュリティベストプラクティスを追えている」と高く評価されます。

### ④ アクセス権付与は「権限セット」で行う

* プロファイルでガチガチに権限を固めるのではなく、「読書記録アプリユーザー」という**権限セット (Permission Set)** を作成。
* LWCへのアクセス権、オブジェクトへのCRUD権限、タブの表示を権限セットに持たせ、「これをユーザーに付与すればアプリが使える」というモダンな運用設計にする。

## 3. 💾 データ抽出スクリプト（ローカル保存）

DE環境が消える、または別の環境にデータを移したい時は、**Salesforce CLI (`sf` コマンド)** を使うのが一番簡単です。

ローカルPCのターミナルで実行するためのコマンドメモです。

**CSVでバックアップを取るコマンド**

```bash
# 接続している組織から、全レコードをCSV形式でローカルにエクスポート
sf data query --query "SELECT Id, Title__c, ISBN__c, ReadDate__c, Category__c, Description__c FROM ReadingLog__c" --result-format csv > reading_logs_backup.csv

```

※定期的にこのコマンドを叩くだけで、手元にCSVとしてデータが残ります。

## 4. 🚀 新規環境（新しいDE）への「一式デプロイ」手順

「DE組織が消えても、新しい環境に5分で元通り構築できる」状態にしておくための、ソース駆動開発（Source-driven development）の基本手順です。

### 準備（今のDE環境があるうちに行うこと）

1. ローカルPCに Salesforce CLI と VS Code をインストール。
2. VS CodeでSFDXプロジェクトを作成 (`sf project generate -n ReadingApp`)。
3. 今の開発環境からソース（オブジェクト、LWC、Apex、権限セット、ダッシュボード等）をローカルに引っ張ってくる。
```bash
sf project retrieve start

```


4. 引っ張ってきたソースコードを **GitHub にプッシュして管理** する（最強のアピールポイント）。

### 復旧（新しいDE環境を作ったときに行うこと）

新しい組織を作成したら、以下のコマンドを順に叩くだけでアプリが一瞬で蘇ります。

```bash
# 1. 新しい組織にログイン
sf org login web --set-default

# 2. GitHub等から落としてきたローカルのソース（一式）を新環境へデプロイ
sf project deploy start

# 3. ユーザーに権限セットを付与（自分にアプリの利用権限を与える）
sf org assign permset --name ReadingAppUser

# 4. (オプション) バックアップしていたCSVデータをインポート
sf data import bulk --sobject ReadingLog__c --file reading_logs_backup.csv

```

### まとめ

このメモの内容を実際に手を動かして形にできれば、**「要件定義 → フロント・バックエンド開発 → 外部API連携 → セキュリティ設計 → バージョン管理・CI/CD基礎」** を全て一人で回せるレベルのエンジニアとして、即戦力扱いされるはずです。
